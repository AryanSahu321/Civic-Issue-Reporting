Aapka sochna **bilkul 100% sahi aur industry-standard** hai! Aapne jo point uthaya hai—ki agar ek hi jagah se multiple reports aa rahi hain, toh iska matlab wahan sach mein bada issue hai—yeh real-world GovTech / Smart City platforms ka core logic hota hai.

Aayiye samajhte hain ki is problem ko real-world mein architectural level par kaise implement kiya jata hai:

---

### 1. Kya hamein duplicate post database mein rakhni chahiye ya delete karni chahiye?

**Database mein duplicate post ki image aur text ko baar-baar store karna bilkul galat hai.** Kyunki isse storage waste hoti hai, database ka size badhta hai, aur queries slow ho jati hain.

Iska industry-standard solution yeh hai:

* **Master-Duplicate Architecture:**
1. Pehli baar jo post aati hai, usko **Master Issue** bana kar database mein save kiya jata hai aur uska ek unique `issue_id` banta hai.
2. Jab doosra user same jagah aur same issue ki photo bhejta hai, toh system usko ek naye issue ki tarah save nahi karta. Balki usko **Duplicate/Upvote Log** ki tarah treat karta hai.
3. Image aur text ko discard kar diya jata hai (ya sirf ek audit trail ke liye chhota reference rakha jata hai), aur master post ke andar ek counter badh jata hai—jaise `report_count = 2` ya ek alag `issue_upvotes` table mein user ki entry daal di jati hai.



---

### 2. Priority aur Ranking Kaise Decide Hoti hai?

Jab multiple log ek hi issue ko report karte hain, toh authority ke dashboard par uski priority automatically upar chali jati hai. Isko bolte hain **Crowdsourced Priority Scoring**:

* **Formula Example:** `Priority Score = (Base Severity by YOLO AI) + (Number of Reports * WeightFactor) + (Days Pending)`
* Agar ek pothole ko 10 alag-alag local logon ne report kiya hai, toh system samajh jata hai ki yeh public ke liye ek major hazard hai. Uska Priority Score spike ho jata hai aur woh Ward Admin ke dashboard par **"High Priority / Hotspot"** section mein sabse upar dikhne lagta hai.

---

### 3. User ko kya Experience (UX) milta hai?

Jab doosra user same issue ki photo khinch kar upload karta hai, toh backend spatial clustering aur pHash match karke turant pehchan leta hai ki yeh already reported hai. Us waqt user ko ek smart response dikhaya jata hai:

> *"Thanks for reporting! This issue has already been logged by another neighbor in your area (Issue ID: #CIVIC-8942). We have added your report to increase its priority. You can track its live status here."*

Is approach ke bohot saare fayde hain:

1. **Server & Storage Cost Bachti hai:** S3 bucket aur PostgreSQL database par extra images ka load nahi padta.
2. **Transparency milti hai:** User ko pata chalta hai ki unki awaaz sun li gayi hai aur unka effort count ho gaya hai.
3. **Clutter nahi hota:** Ward officers ke paas 50 alag-alag photos nahi aatiin, balki ek hi main issue aata hai jis par likha hota hai *"Reported by 12 citizens"*, jisse woh bina spam ke jaldi action lete hain.

Is feature ko implement karne ke liye humein **Authentication, Database Mapping, aur State Tracking** ka ek clean flow banana hoga. Kyunki aapne decide kiya hai ki hum Aadhaar nahi lenge, balki **Mobile Number + OTP** ya **Secure Username/Password** se user ko authenticate karenge, toh yeh system bilkul smooth aur privacy-friendly rahega.

Isko step-by-step implement karne ka real-world architecture aur code workflow yeh hai:

### Step 1: Database Schema Update (Linking Posts to Users)

Aapke PostgreSQL database mein `posts` table ke andar pehle se `user_id` ka foreign key maujood hai jo `users` table se connected hai. Jab bhi koi user login karke post submit karega, uska `user_id` us post ke sath permanently save ho jayega.

* **Master & Duplicate Table Mapping:**
* **`posts` (Master Issue Table):** Har unique problem ka ek main record hota hai (`post_id`, `user_id`, `location`, `status`, `image_url`).


* **`issue_reports` (Upvotes / Duplicate Logs Table):** Agar koi doosra user same jagah aur same issue ki duplicate photo bhejta hai, toh hum nayi post create nahi karte. Balki is table mein entry daal dete hain:
```sql
CREATE TABLE issue_reports (
    report_id SERIAL PRIMARY KEY,
    post_id INT REFERENCES posts(post_id),
    user_id INT REFERENCES users(user_id),
    created_at TIMESTAMP DEFAULT NOW()
);

```


Isse pata chal jata hai ki kis-kis user ne is issue ko support/report kiya hai, aur master post ka counter badh jata hai.



---

### Step 2: Backend API Implementation (Node.js / Express)

User jab app mein login karta hai, toh use ek **JWT Token** milta hai. Jab woh status track karne ke liye request bhejta hai, toh hum sirf usi user ki bhejhi gayi ya upvote ki gayi posts fetch karte hain.

* Tracking Endpoint (`GET /api/v1/citizens/track`):



```typescript
import { Router, Response } from 'express';
import { verifyJWT, AuthenticatedRequest } from '../middleware/auth.middleware';
import { PrismaClient } from '@prisma/client';

const router = Router();
const prisma = new PrismaClient();

router.get('/track', verifyJWT, async (req: AuthenticatedRequest, res: Response) => {
  try {
    const userId = req.user?.userId;

    // Fetch posts created by the user OR backed by the user in issue_reports
    const userIssues = await prisma.post.findMany({
      where: {
        OR: [
          { user_id: userId },
          { reports: { some: { user_id: userId } } }
        ]
      },
      include: {
        ward: true, // Shows which municipal ward is handling it
      },
      orderBy: { created_at: 'desc' }
    });

    return res.status(200).json({
      status: 'success',
      count: userIssues.length,
      data: userIssues
    });
  } catch (error) {
    console.error(error);
    return res.status(500).json({ error: 'Internal Server Error' });
  }
});

export default router;

```

### Step 3: Duplicate Submission Logic & UX Handling

Jab user koi nayi photo upload karta hai, toh backend par spatial check (Radius < 10 meters) aur pHash / Visual embedding check run hota hai:

1. **Agar Issue Naya Hai:**
* System ek naya record `posts` table mein insert karta hai aur status `PENDING_NLP` set kar deta hai.




2. **Agar Issue Pehle se Reported Hai (Duplicate):**
* System nayi image ko discard kar deta hai (storage cost bachti hai).


* `issue_reports` table mein ek naye row insert karke current user ko us existing master post se link kar deta hai.
* API response mein user ko ek friendly message milta hai:
> *"This issue was already reported nearby. We have linked your account to it to increase its priority!"*

### Step 4: Frontend (React Native) User Experience

* **My Reports / Tracking Screen:** App ke andar ek dedicated tab hota hai jahan user apni saari reported problems ki list dekh sakta hai.
* Har issue ke samne uska live status dikhta hai—jaise **`Pending`**, **`Assigned to Ward`**, **`Under Process`**, ya **`Resolved`**.


* Agar kisi issue par doosre logon ne bhi report kiya hai, toh wahan ek badge show hota hai: *("Reported by 14 local citizens - High Priority")*. Isse user ko transparency milti hai ki unka effort count ho raha hai aur system real action le raha hai.
